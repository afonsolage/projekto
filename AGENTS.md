# AI Usage Policy

This file mirrors and extends the "AI Usage" section of [README.md](README.md#ai-usage). It
applies to any AI/assistant (including coding agents) working on this repository.

## Language

The main and default language of the project is en-US. Code, documentation, comments, commit
messages and AI-assisted output are written in that language unless the author asks otherwise.

## Rules

- **AI may write code, but every AI-written change must be reviewed and refined by a human.**
  The author must understand every line and be able to explain its rationale and tradeoffs. This
  applies to tests as well.
- **AI may be used for** writing code, reviewing architecture concepts, knowledge checking,
  generating documentation (e.g. [ARCHITECTURE.md](ARCHITECTURE.md)) and drafting PR titles and
  descriptions.
- **Always disclose AI-generated content.** Whenever AI is used to produce something, state it,
  including in the PR description when AI wrote code. [ARCHITECTURE.md](ARCHITECTURE.md) carries
  a disclaimer because it is AI-generated and reviewed by the author before committing.

## What this means in practice

- AI may implement changes, but never merges them: every AI-written change is handed to a human
  for review and refinement.
- Run the CI checks (`just ci`) and the adversarial review before asking for human review.
- Do not add e.g. "Generated by ..." comments to source files; disclosure belongs in prose
  (commit message, docs, or the conversation), not in the code.

## Writing documentation and comments

Any text an AI produces in this repository - docs, doc comments, inline comments, commit
messages - must be reviewed and owned by a human before it lands. In particular:

- **No thinking leakage.** Do not leave the model's reasoning process in the output: no
  "wait", "actually", "let me reconsider", no lists of alternatives that were considered and
  discarded, and no notes-to-self left over while drafting. The final text must read as
  deliberate, finished documentation.
- **No meta-commentary.** Do not describe the assistant, the act of generating, or the request
  itself ("as an AI", "the following was generated", "here is the documentation you asked
  for"). State the facts directly.
- **Match the existing documentation style.** Before writing, read the surrounding docs
  ([README.md](README.md), [ARCHITECTURE.md](ARCHITECTURE.md)) and follow their conventions:
  sentence-case headings, concise declarative prose, the project's terminology (`Chunk`,
  `Kind`, `Side`, `Face`, ...), and code references in the existing link format
  (``[`symbol`](path#Lnn)``). Do not introduce heading levels, emojis or formatting the rest
  of the project does not already use.
- **No duplication or padding.** Do not restate the same thing in prose, doc comments and
  inline comments at once, and do not explain what the code already says clearly.

## Posting PR comments and reviews

`gh pr review` and `gh pr comment` create a new review or comment on every invocation. They are
not idempotent and print nothing on success, so they must be sent once and verified by reading
the result back, not by re-running them.

- Post once, then confirm with `gh pr view <number> --json reviews` (or the equivalent query for
  the comment type) before considering the step done.
- Treat an empty output as a possible success, not a failure. Never re-run a side-effecting
  command just because its stdout was empty; check the PR state first and skip the call if the
  comment already exists.
- Do not wrap `gh pr review` or `gh pr comment` in loops or automatic retries.
- A submitted review cannot be deleted: `DELETE
  /repos/{owner}/{repo}/pulls/{number}/reviews/{id}` only removes *pending* reviews. A duplicate
  can only be minimized (`minimizeComment`), not removed, so prevention is the only reliable fix.

## CI checks before review

This repository runs GitHub Actions on every PR, on a pinned nightly toolchain (see
[`.github/workflows/ci.yaml`](.github/workflows/ci.yaml)): `cargo test --workspace`, `cargo
clippy --workspace --all-targets -- -D warnings`, `cargo fmt --all -- --check` and `cargo
udeps`. The same validations run locally with `just ci`. CI often catches common failures, so
before spawning the adversarial review or asking the user to review, monitor the checks of the
open PR until they finish.

- Always monitor the PR checks; do not consider the PR ready while any check is failing or
  still pending. Use `gh pr checks <number> --watch` to follow them to completion.
- If a check fails, investigate and fix it before requesting review. If the failure is
  pre-existing on `main` and unrelated to the change, say so explicitly instead of ignoring it.
- Useful commands: `gh pr checks <number>` and `gh run view <run-id> --log-failed`.

## Adversarial review before a PR

Before opening a PR, or asking a human to review it, spawn the `adversarial-review` subagent
(defined in [`.opencode/agent/adversarial-review.md`](.opencode/agent/adversarial-review.md))
to check the change. It is fine-tuned to this project and the Bevy ecosystem: its job is to
actively try to falsify the work, catching real bugs, Bevy ECS pitfalls, protocol/serialization
breaks and voxel-specific edge cases.

- Required when the change is substantial, or whenever the user explicitly asks for it.
- Not required for every follow-up push or minor update to an already-open PR.
- Do not ask for review until the blocking findings are fixed or consciously dismissed by the
  author.

## Aligning with Bevy's AI policy (proposal for review)

This project follows Bevy Org best practices, so the table below maps Bevy's
[AI Policy](https://bevy.org/learn/contribute/policies/ai/) onto this repository.

| Bevy norm | Proposed here |
| --- | --- |
| No AI-generated media | Adopt. Textures, models and audio must be hand-made or permissively licensed; `assets_src/` holds the hand-authored sources. |
| No AI-generated prose | Partially adopt. AI may still draft documentation (as the README already allows) and PR titles/descriptions, but a human must review, rewrite where needed and own the result before it lands. AI output is not pasted directly into issue comments or human conversations. |
| No AI-generated communication | Adopt. Talk to people directly; do not paste AI output into human conversations. |
| No AI-authored commits | Adopt. Commits are authored by humans; no AI `Co-authored-by`. |
| Ownership | Adopt. The author understands every line submitted and can explain its rationale. |
| Disclosure | Adopt. Already covered above and in [ARCHITECTURE.md](ARCHITECTURE.md). |
| Quality | Adopt. AI-assisted changes are held to the same review bar as hand-written ones. |
| Harassment | Adopt. Do not harass, demean or pressure others; keep the discussion civil. |
| Refusal | Adopt. No one is required to review AI-assisted work or use AI tools. |

AI-written code is allowed here under the **Ownership**, **Disclosure** and **Quality** norms:
a human reviews, refines and owns every change before it lands.

Bevy's policy fully bans AI-generated prose, which conflicts with this project's current
allowance for AI-generated documentation and AI-drafted PR titles/descriptions. The "Partially
adopt" row is the proposed compromise; strict adoption would mean dropping AI-generated docs
such as [ARCHITECTURE.md](ARCHITECTURE.md) and hand-writing every PR title and description.
