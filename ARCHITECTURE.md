# Project Architecture

This document outlines the architecture of the project, with a focus on the
Entity-Component-System (ECS) design of both the client and server.

## Client

The client is responsible for rendering the world and handling user input. It connects to the
server to get the world data and send player actions. It keeps no voxel data: every chunk exists
on the client only as a mesh.

### Terrain textures

Terrain is rendered from an atlas generated at runtime by the
[`projekto_textures`](./crates/textures/Cargo.toml) crate. No terrain spritesheet is shipped or
loaded: [`generate_atlas`](./crates/textures/src/lib.rs#L83) synthesizes a 320×320 atlas of 32×32
tiles from the world seed, and the mesher keeps using the tile offsets declared in
[`kind.ron`](./assets/voxels/kind.ron).

Materials are authored data ([`MATERIALS`](./crates/textures/src/materials.rs#L201)): periodic
noise fields plus per-material motifs such as grass tufts, rock cracks and strata, sand ripples,
snow hollows, moss cushions and lamp facets. Complex blocks compose several materials through
procedural masks ([`LayerMask`](./crates/textures/src/layers.rs#L14)): a grass side is dirt with a
grass band on top, and snow and moss sides use the same pattern. An art preset
([`ArtPreset`](./crates/textures/src/art.rs#L30)) sets shade count, contrast, chroma and color
temperature; the default is `soft`.

The world seed arrives through the [`ServerInfo`](./crates/messages/src/lib.rs#L28) message when
the connection is established. Until then the client uses
[`FALLBACK_WORLD_SEED`](./crates/client/src/textures.rs#L24), so every client renders the same
textures for the same world without transferring image data.

Message handlers are registered with the `proto` crate instead of being added to a schedule.
`handle_messages` runs them inline while it drains the channel, so they execute in `PreUpdate`
on the frame their message arrives.

### System Sets (ClientSet)

2.  **`Update`**:

3.  **`PostUpdate`**:
    - `SendInput`, gated on `ServerConnection`:
      - `update_landscape_center` (`SendInputPlugin`)
      - `update_player_landscape` (`SendInputPlugin`), when `PlayerLandscape` changed
      - `send_welcome_message` (`SendInputPlugin`), when `ServerConnection` was added

The server is responsible for managing the game world, including world generation, chunk

## World pipeline

### World generation

[`TerrainGenerator`](./crates/server/src/genesis/terrain/mod.rs#L46) builds each chunk from a
validated [`WorldGenConfig`](./crates/server/src/genesis/terrain/config.rs#L11). Two low-frequency
turbulence fields warp the shape sampling position, and the warped coordinates feed continentalness,
erosion, weirdness, the landform mask and the upheaval field. The landform mask blends two height
profiles, `landform_plains` and `landform_mountains`, over continentalness, so plains and mountain
regions have genuinely different vertical scale rather than different noise amplitude. The upheaval
field adds tectonic uplift, strongest in mountain landforms, and erosion controls a small
peaks-and-valleys relief term. [`landform_weight`](./crates/server/src/genesis/terrain/mod.rs#L370),
[`soft_clamp_height`](./crates/server/src/genesis/terrain/mod.rs#L424) and
[`terrace`](./crates/server/src/genesis/terrain/mod.rs#L442) keep the vertical profile continuous and
compress rare peaks asymptotically instead of flattening them against a hard ceiling.

Climate samples temperature and humidity at unwarped coordinates, and
[`BiomeTable::weights_into`](./crates/server/src/genesis/terrain/biome.rs#L104) selects the nearest
biome entry in `(temperature, humidity, erosion)` space and returns normalized blend weights. Ties
resolve by table order, and the dominant index keeps the squared-distance comparison used before
blending. [`BiomeTable::blended_shape`](./crates/server/src/genesis/terrain/biome.rs#L181) sums each
entry's five shape fields over those weights: height offset, relief multiplier, terrace strength,
cave density and overhang strength. The
[`sample_column`](./crates/server/src/genesis/terrain/mod.rs#L121) helper combines the landform
profile, uplift and biome shape, applies one smoothed staircase terrace and the soft top clamp, and
returns the cached column values. The
[`samples`](./crates/server/src/genesis/terrain/mod.rs#L189) helper caches an 18x18 column halo per
chunk, so height, slope, biome and 3D parameters are read once per world column.

[`SurfaceRule::kind`](./crates/server/src/genesis/terrain/surface.rs#L29) maps depth and slope to a
kind: the selected surface biome's top, its subsurface for `subsurface_depth` voxels, the shared
steep kind above `max_slope`, and the shared deep kind below. The fill pass uses the cached
overhang strength and cave density to lift the surface and scale the cavern threshold per column.
Inside a transition band,
[`BiomeTable::surface_biome`](./crates/server/src/genesis/terrain/biome.rs#L154) picks the surface
biome from the blend weights using a deterministic, uniform jitter derived from a cell hash, so
materials interleave over the transition band instead of switching at a hard border. The
`material_blend_cell` setting controls the patch size, and uniform jitter makes each material's
share follow its weight. Climate frequencies are low enough that biome cores span hundreds of
blocks.

[`worldgen.ron`](./assets/worldgen.ron) ships five biomes: Plains (Grass over Dirt), Forest
(Moss over Dirt), Desert (Sand over Sand), Tundra (Snow over Dirt) and Roughlands (Rock).
[`kind.ron`](./assets/voxels/kind.ron) binds each biome surface to generated materials: `Grass`
uses a grass top, a composite grass-over-dirt side and dirt below, `Moss` and `Snow` use the same
pattern with moss and snow bands, and `Sand` uses one sand tile on every face. The atlas and all
tiles are synthesized at runtime by the client (see [Terrain textures](#terrain-textures)); the
per-kind [`KindSideTexture::color`](./crates/core/src/voxel/kind.rs#L13) multiplier applied by
[`generate_vertices`](./crates/server/src/meshing/mod.rs#L52) and
[`generate_coarse_vertices`](./crates/server/src/meshing/lod.rs#L66) is neutral `(1, 1, 1, 1)` for
every shipped kind, and remains available for future per-biome tints.

Changing the generated world requires bumping
[`VERSION_MAGIC`](./crates/archive/src/lib.rs#L58) and deleting the local `archive/region`
directory before a clean visual run. Per-asset reads reject older magic, and the server warns and
regenerates stale chunks loaded from an old archive.

### Chunk storage

A chunk is a 16×256×16 grid indexed by [`ChunkVoxel`](./crates/core/src/coords/chunk.rs#L99);
[`ChunkStorage<T>`](./crates/core/src/chunk/storage.rs#L28) stores one layer of it and selects
its backend at compile time through
[`ChunkStorageType::USE_SECTIONS`](./crates/core/src/chunk/storage.rs#L14).

`Kind` and `Light` use the section backend
([`SubChunkStorage`](./crates/core/src/chunk/sub_chunk.rs#L60)): the chunk is split into 16³
sections, and each section is one of [`ChunkPack`](./crates/core/src/chunk/sub_chunk.rs#L426)'s
forms — `Single` for a uniform section, `Pallet` for a palette plus bit-packed indices, and
`Dense` when a section has more than 255 distinct values. `pack` re-encodes a section into the
smallest form. The derived layers, `FacesOcclusion` and `FacesSoftLight`, use the column backend
([`ChunkColumnStorage`](./crates/core/src/chunk/column.rs#L21)), which packs each vertical
16-voxel column into `Single` or palette form. Columns are not persisted; they are rebuilt from
`Kind` and `Light` when needed.

The backend tag is part of the serialized form. A `ChunkStorage<T>` decoded with the wrong
backend for `T` is rejected rather than reinterpreted.

### LOD and asynchronous meshing

Server meshing has two detail tiers. [`desired_lod`](./crates/server/src/set/meshing.rs#L102)
keeps chunks inside the [`LOD_FULL_RADIUS`](./crates/server/src/set/meshing.rs#L85) square (16
chunks) around the landscape centre at LOD 0 and gives the rest LOD 1.
[`next_lod`](./crates/server/src/set/meshing.rs#L120) adds
[`LOD_HYSTERESIS`](./crates/server/src/set/meshing.rs#L90) for chunks already at LOD 0, so a
chunk oscillating around the boundary is not remeshed every frame.
[`update_chunk_lods`](./crates/server/src/set/meshing.rs#L138) applies at most
[`LOD_UPDATES_PER_FRAME`](./crates/server/src/set/meshing.rs#L93) transitions per update and
dirties the chunk and its horizontal neighbours because the seam changes. The coarse mesher
([`LodScale`](./crates/server/src/meshing/lod.rs#L26)) downsamples x and z by `2^lod` (capped at
16) and keeps the full vertical resolution, so horizontal overhangs remain visible.

[`mark_dirty_chunks`](./crates/server/src/set/meshing.rs#L191) turns a `Kind` change into a
three-by-three dirty region and drops both derived caches; a `Light` change dirties the same
region but keeps the occlusion cache, which only depends on kinds. A chunk that still carries
`CachedMesh` skips the initial pass.

[`generate_vertices`](./crates/server/src/set/meshing.rs#L287) never meshes on the ECS thread.
It imports finished [`MeshTasks`](./crates/server/src/set/meshing.rs#L54), discards results for
chunks that were re-dirtied, unloaded or whose LOD changed, then admits at most
[`MESH_MAX_SPAWNS`](./crates/server/src/set/meshing.rs#L46) tasks per update while fewer than
[`MESH_MAX_IN_FLIGHT`](./crates/server/src/set/meshing.rs#L43) are running. Candidates are sorted
nearest-first, alternate between full and coarse so neither starves, and wait until the chunk's
halo is loaded. Full meshes store occlusion and soft light in
[`DerivedCaches`](./crates/server/src/cache.rs#L14); coarse meshes do not populate those caches.

### Streaming

`PlayerLandscape` follows the active camera. The client sends a `LandscapeUpdate` when its
centre or radius changes and once when the connection is established. The server clamps the
radius to [`MAX_LANDSCAPE_RADIUS`](./crates/server/src/set/landscape.rs#L22) (32) and replaces
the `Landscape` resource.

[`update_landscape`](./crates/server/src/set/landscape.rs#L41) walks the requested square and
emits `ChunkLoad` nearest-first, plus `ChunkUnload` for every mapped chunk outside the square.
[`chunks_load`](./crates/server/src/set/chunk_management.rs#L204) keeps a loading set so a
pending chunk is not requested twice, reads the archive first and falls back to `GenesisServer`
on a miss, and drops any result that arrived after the chunk left the landscape. Saved chunks are
spawned with the LOD they should use now; a changed LOD, an old mesh version or an empty mesh over
solid terrain marks them dirty.
[`chunks_unload`](./crates/server/src/set/chunk_management.rs#L147) cancels the chunk's mesh
task, invalidates its neighbours, updates client bookkeeping and despawns the entity.

Client updates use a bounded channel. [`ClientSync`](./crates/server/src/net.rs#L50) remembers
which chunks have pending updates and unloads per client, and retries the ones that did not fit,
so a slow client never blocks the ECS thread.

### Persistence

Chunks are stored in region files under `archive/region/{x}_{z}.rgn`, one file per 32×32 chunk
region. A file starts with a 4096-byte header holding one 4-byte sector index per chunk; each
asset is bincode-encoded, lz4-compressed and prefixed with
[`VERSION_MAGIC`](./crates/archive/src/lib.rs#L58). [`ArchiveServer`](./crates/archive/src/server.rs#L162)
owns one worker per region on the I/O task pool, so reads, writes, compression and header flushes
do not run on the ECS thread.

[`ChunkAsset`](./crates/archive/src/asset.rs#L17) stores `kind`, `light`, `vertex`, `lod` and
`mesh_version`. [`CHUNK_MESH_VERSION`](./crates/archive/src/asset.rs#L10) is bumped whenever the
mesher output changes; a mesh saved by an older version is loaded but not trusted, so the chunk
is remeshed. A missing asset, an unsupported archive version or a decode failure is regenerated
through `GenesisServer`.

[`queue_chunks_to_save`](./crates/server/src/set/chunk_management.rs#L423) only queues chunks
whose `ChunkVertex` changed. It skips placeholder empty buffers and cached meshes that were not
rebuilt.
[`chunks_save`](./crates/server/src/set/chunk_management.rs#L468) persists at most 64 chunks
every 0.25 s, drops chunks without a `ChunkLod`, and never saves a chunk that is dirty or has a
mesh task in flight.
[`archive_maintenance`](./crates/server/src/set/chunk_management.rs#L104) flushes dirty headers
every 2 s and again when a save burst drains, which is what makes saved chunks visible to the
next session.

## `proto` Crate

The `proto` crate is responsible for the communication protocol between the client and the
server. It defines the messages that can be sent and received, and it handles the
serialization and deserialization of these messages.

### `message_source` Macro

The `message_source` macro is the core of the `proto` crate. It takes an enum definition and
generates the necessary code to handle the serialization, deserialization, and handling of the
messages defined in the enum. The macro generates a simplified version of the enum, a struct
for each enum variant, and the necessary trait implementations.

### Traits

- **`MessageType`**: This trait is implemented for the simplified enum generated by the
  `message_source` macro. It defines the methods required to handle the messages, such as
  getting the message code, serializing and deserializing the message, and running the message
  handlers.

- **`Message`**: This trait is implemented for the structs generated by the `message_source` macro.
  It defines the methods required to get the message type and source.

- **`NoCopy`**: This marker trait is used to indicate that a message should not be copied when
  handled. This is useful for messages that contain large amounts of data, such as the
  `ChunkVertex` message.

### Type Erasure

Type erasure is used to handle the messages in a generic way. The `message_source` macro
generates a `BoxedMessage<T>` type alias, which is a boxed trait object of the `Message<T>`
trait. This allows the messages to be stored in a collection and handled without knowing their
concrete type.

### Adding a New Message

To add a new message, you need to add a new variant to the `ClientMessage` or `ServerMessage`
enum in the `messages` crate. The `message_source` macro will automatically generate the
necessary code to handle the new message.

For example, to add a new `MyMessage` message, you would add the following to the
`ClientMessage` enum:

```rust
#[message_source(MessageSource::Client)]
enum ClientMessage {
    // ...
    MyMessage { a: u32, b: bool },
}
```

Then, you need to add a handler for the new message. The handler is a system that takes the
message as a parameter using the `In` system param. For example:

```rust
fn handle_my_message(In(message): In<MyMessage>) {
    // ...
}
```

Finally, you need to register the message handler in the client or server app:

```rust
app.add_message_handler(handle_my_message);
```


## Debug tooling

Debug tooling is feature-gated: `debug-tools` enables shared data, UI plugins and BRP, and the
AI client is a separate binary that requires it. Normal release builds do not compile
`projekto_debug` or collect chunk debug data. The binaries add the optional
`ClientDebugPlugins`/`ServerDebugPlugins` groups.

- **`projekto_debug`**: debug data and client/server/AI plugins shared by the debug binaries:
  `ChunkDebug`, `DebugPin`, `DebugViewConfig`, stable chunk ids and chunk colours.
- **Client debug overlay** (`crates/debug/src/client`): chunk grid and coordinate labels (F4/F5),
  hovered-chunk summary, world pins (F8/F9), the RAM overlay (F3) and debug report capture (F7).
  Reports contain a screenshot, camera/hovered/nearby chunk data, pins and memory.
- **Remote API**: with `debug-tools`, the server and client expose the Bevy Remote Protocol over
  HTTP on `127.0.0.1:15702` (and `15703` for the render subapp). Custom methods
  cover chunk inspection, pins, reports and controlled mutations such as remesh, teleport and
  set-voxel.
- **`projekto-archive` CLI**: `just archive info|list|holes|verify|dump` reads region archives
  offline, with `--json` output for automated diagnostics.

See [docs/debug-tools.md](docs/debug-tools.md) for hotkeys, BRP examples and report format.
